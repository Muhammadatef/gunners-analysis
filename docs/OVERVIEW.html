GunnersAnalysis · football intelligence platform

Architecture, and how to actually run it

A Premier League event-data pipeline with an analyst on top of it. The pipeline turns two match URLs into a warehouse row and eighteen rendered panels. The analyst answers questions about what it collected, and is built so that it cannot invent a statistic.

01 · the shape of it

Two halves that meet in Postgres

Everything before Postgres is collection: scrape a match, align it with a second source, check it, render it, load it. Everything after Postgres is interpretation: derive the tactical layer Opta never records, write it up as prose, embed it, and answer questions against it.

The database is the seam. Numbers only ever cross it in one direction, which is what makes the analyst's central guarantee possible: every figure in an answer traces back to a query that returned it.

02 · collection

Seven stages, in this order

Order matters here, so it is numbered. Each stage is a plain function in orchestrator/pipeline.py, which is why a DAG task, an HTTP request and a CLI run all execute identical code rather than three drifting copies.

  1. Resolve scraper/fixtures.py Turn a calendar slug into a real WhoScored match id. Ids are only minted a few weeks before kick-off, so the calendar stores the slug and this looks it up when the time comes.
  2. Scrape scraper/scraper.py A real Chrome session — headed on a desktop, Xvfb in a container, headless only as a last resort — pulls the match centre page and waits for the event payload rather than sleeping a fixed interval.
  3. Transform transformer/transform.py The embedded JSON becomes events, players and metadata. Competition and team colours are set here, so a non-English club is not silently labelled Premier League or painted in Arsenal red.
  4. Enrich scraper/sofascore.py xG and xGOT come from the second source. Before anything is written, the two feeds' home and away sides are compared — a mispasted link produces a refusal, not confident wrong numbers.
  5. Validate quality/checks.py Thirteen checks, and a hard gate: event count in range, full ninety minutes covered, eleven starters a side. A match that fails does not reach the warehouse.
  6. Render visualizer/match_report.py Eighteen panels plus a unified dashboard, into output/[club]/season/match/, with a season index and a _latest pointer maintained per club.
  7. Load db/loader.py Upserts into that club's schema. Re-running the same job replaces its child rows rather than duplicating them, so a retry is safe.
one club, one schema

Nothing in the codebase writes schema-qualified SQL. The schema is chosen once per connection via search_path, so Arsenal stays in gunners and --club barcelona gets a full clone of the same DDL. Pass the club; never hand-edit a table name.

03 · interpretation

Why the analyst cannot invent a number

This is architecture, not an instruction in a prompt. Three mechanisms, all mechanical, and a fourth rule that is measured rather than hoped for.

  • It never writes SQL. It picks an id from a registry of 17 allowlisted, parameterised queries and supplies the arguments. The worst mistake available is choosing the wrong query — a routing error the evaluation measures.
  • It never does arithmetic. Ratios and differences go through a calculator that walks the expression's syntax tree. No names, no attributes, no imports exist to it.
  • Every number is checked before the answer is returned. Each figure in the draft is matched against the set the evidence actually vouched for; anything unmatched is reported as unsupported_numbers.
  • It refuses rather than guesses. Injuries, transfer fees, other clubs' players, next season, per-shot xG — the evaluation set contains questions whose only correct answer is a refusal, scored separately.

05 · three ways in

Pick the path that matches the job

These are parallel routes into the same seven stages, not steps in a sequence. Choose by what you have: a scheduled fixture, a single match you want to watch run, or a whole season already played.

automatic

A scheduled Arsenal fixture

One DAG per fixture, firing 2h25 after kick-off — the match plus stoppage, plus thirty minutes for the feed to settle. Nothing to run.

manual

One match, any club

Two links in, one match out. This is the entry point for Barcelona, a Champions League tie, Al Ahly — anything outside the Arsenal calendar.

bulk

A season already played

Derive the calendar from SofaScore, then ingest match by match. Resumable: re-run after any failure and it picks up where it stopped.

05a

One match, from two links

--club chooses the Postgres schema and the output directory, and is validated before anything is scraped so a typo fails in a second rather than after a page load. The SofaScore link is required unless you explicitly pass --no-xg — rendering a report with placeholder zeros is worse than an error. 

make match CLUB=barcelona \
  WS='https://www.whoscored.com/matches/<id>/live/<slug>' \
  SS='https://www.sofascore.com/football/match/<slug>/<id>' \
  COMP='Champions League' MW=6

# or directly, for the full set of flags
python orchestrator/run_match.py --club barcelona \
  --whoscored '<url>' --sofascore '<url>' \
  --season '2025/2026' --competition 'Champions League' \
  --home-color '#A50044' --away-color '#FEBE10'

Prints the job id, the schema, the match directory, the xG source and the final line. Exits non-zero on failure, so it composes into a shell script.

05b

A whole finished season

make calendar BACKFILL_SEASON='2025/2026'   # derive it from SofaScore
make backfill-plan                          # what would run, touching nothing
make backfill                               # ~40 min for 38 matches, resumable
make readiness                              # enough history to analyse?

make backfill-plan first, always. It is the difference between finding a wrong season string in two seconds and finding it forty minutes in.

06 · the analyst

Asking it things

Build the layer once — derived tactical tables, the document corpus and its embeddings, the evaluation set — then ask. Both commands need LOCAL=1, and the reason is worth knowing.

the analyst runs on the host, not in a container

Its dependencies cannot be installed into the Airflow image: the agent's ORM needs SQLAlchemy 2, Airflow 2.10 forbids it, and pip resolves that conflict with a warning and a successful build that then cannot load Airflow's own data model. LOCAL=1 runs against the project virtualenv, which has no Airflow in it and therefore no conflict. 

# the compose default points at the container hostname; override it on the host
export GUNNERS_DB_URL='postgresql://gunners:<password>@localhost:5432/gunners'

LOCAL=1 make agent-setup   # tactical tables, documents, eval set, gates

LOCAL=1 make ask Q="Was Arsenal a high-pressing side in 2025/26?"
LOCAL=1 make ask Q="How many points did Arsenal take in 2025/26?"

That second question returns:

Arsenal finished the 2025/2026 season with 85 points.

The last line is the point of the whole design. Read it every time.

06a

Measuring it

130 questions across 18 families, split by family rather than at random — a random split would put “how many goals did Saka score” in training and the same question about Rice in test, and reward memorisation. Three model tiers, and which one you are on matters more than anything else in the configuration.

TierModel$ / 1M in · outUse it for
wiringgpt-oss-20b:free0 · 0plumbing and smoke tests only
cheapgpt-oss-20b0.03 · 0.13evaluation and optimizer runs
qualityclaude-sonnet-4.53 · 15answers you intend to act on
 
LOCAL=1 make eval SPLIT=dev  TIER=wiring   # free; proves the wiring, not the quality
LOCAL=1 make eval SPLIT=test TIER=cheap    # the held-out split, ~$0.002
# traces and run history: http://localhost:5000
a free-tier score is not a regression check

A call that never reached a model is scored as a wrong answer, exactly like a hallucination. A dev run on the free tier scored 0.111 with 15 of 18 questions rate-limited before they got anywhere — against a recorded baseline of 0.891 on the same split. Use cheap for anything you intend to compare.

07 · honest state

What works, and what does not

CapabilityStateDetail
Match pipeline, end to end proven 38 of 38 matches ingested; every score independently verified against a source the pipeline never touches
xG / xGOT alignment proven all 38 from SofaScore, none on a placeholder
Manual two-link run, any club working own schema and output tree per club
Analyst, from the host working routing, retrieval, the number check, MLflow tracing
The 38 fixture DAGs untested live every stage has 38 real runs behind it; the scheduling wrapper has never fired. First live test is matchweek 1
The 3 agent DAGs blocked SQLAlchemy 2 vs Airflow 2.10; all three are paused. Corpus refresh is manual until they get a separate interpreter
Per-shot xG absent match-level only; “which chance was best” is a question the agent must refuse, and that refusal is measured
Alerting none a DAG failing at 23:00 on a Saturday tells nobody

Two more worth carrying in your head: the weekly evaluation DAG fails below a floor of 0.50 while the measured held-out score is 0.517 — three percent of headroom — and the warehouse holds only Arsenal's matches, so cross-club player comparisons are refusals rather than answers.
