# Season automation

How a fixture on a calendar becomes 19 PNGs and a few thousand Postgres rows,
without anyone touching it.

## The calendar

`airflow/fixtures/arsenal_2026_27.json` holds all 38 Premier League fixtures,
generated by `airflow/fixtures/build_fixtures.py` from the published lists
([Premier League](https://www.premierleague.com/en/news/4675132/all-of-arsenals-fixtures-for-202627-premier-league-season),
[Sky Sports](https://www.skysports.com/football/news/11095/13555674/arsenal-premier-league-2026-27-fixtures-and-schedule) —
cross-checked, both agree on every match).

Each entry looks like:

```json
{
  "matchweek": 17,
  "date": "2026-12-26",
  "kickoff_uk": null,
  "kickoff_confirmed": false,
  "opponent": "Crystal Palace",
  "venue": "A",
  "home_team": "Crystal Palace",
  "away_team": "Arsenal",
  "whoscored_slug": "england-premier-league-2026-2027-crystal-palace-arsenal",
  "fixture_key": "gw17_2026-12-26_crystal-palace_v_arsenal"
}
```

`fixture_key` is the join key across the JSON, the `fixtures` table, and the DAG id.

Four fixtures had a confirmed kick-off when the list was published (MW1, MW13,
MW18, MW20 — all 20:00). The other 34 default to **15:00 UK** until the TV picks
land.

## One DAG per fixture

`airflow/dags/arsenal_season_dag.py` loops the calendar and registers a DAG for
each match:

```
arsenal_2026_2027_gw17_2026-12-26_crystal-palace_v_arsenal
```

Tasks:

```
await_final_whistle → resolve_match_id → scrape → transform → enrich_xg
  → validate → visualize → load_warehouse
  → football_analyst_DSPy_agent_match_report
```

`football_analyst_DSPy_agent_match_report` (UI description: **DSPy football analyst agent match report**)
calls the analyst service `POST /report` after the warehouse load and writes a
panel-cited technical `REPORT.md` into the match folder. It does **not** import
`dspy` inside Airflow (SQLAlchemy pin conflict); set `GUNNERS_REPORT_OPTIONAL=1`
to soft-skip on LM outages.

### Scheduling

Each DAG gets a cron pinned to its own date, via **`CronTriggerTimetable`**
(Europe/London). Do **not** pass a bare cron string — Airflow treats yearly
crons as a year-long data interval and only creates the DagRun at the *next*
anniversary (MW1 2026 never fired for that reason).

| | |
|---|---|
| kick-off | fixture date + `kickoff_uk` (or 15:00) in `Europe/London` |
| final whistle | kick-off + `MATCH_DURATION_MINUTES` (default 115) |
| run time | final whistle + `POST_MATCH_DELAY_MINUTES` (default 30) — kick-off + 2h25 |
| cron | `<minute> <hour> <day> <month> *` (trigger timetable) |
| `start_date` | run time − 1 day |
| `end_date` | run time + 3 days |

The `start_date`/`end_date` bracket is what stops a `day month` cron from firing
again next year. Late kick-offs roll over correctly — MW1's 20:00 kick-off
schedules `25 22 21 8 *` (22:25 UK on the 21st).

Four hours is deliberate: ~2h of football, plus WhoScored's own processing lag.

### Waiting for the whistle

The cron above is only as good as `kickoff_uk`, and **32 of the 38 fixtures do
not have one** — they fall back to `DEFAULT_KICKOFF` (15:00). MW4 kicked off at
20:00, so its DAG fired at 17:25, two and a half hours before the players came
out. No amount of retrying a match-id lookup fixes a run that happened before
the match.

So the first task is **`await_final_whistle`**. It asks FotMob's public JSON
feed (`/api/data/matches?date=…`, no browser, no bot wall) whether this fixture
has actually finished:

* finished → carry on, logging the real kick-off next to the scheduled one so a
  wrong `kickoff_uk` shows up in the task log
* not finished → raise, and retry. `WHISTLE_RETRIES` × `WHISTLE_RETRY_DELAY_MINUTES`
  defaults to 24 × 15 min = **6 hours**, which covers a whole afternoon of being
  wrong about kick-off
* cancelled, or not listed for that date → skip / raise respectively; a
  postponement is not something to wait six hours for

A note on the retry that was not: **`AirflowSkipException` does not retry.** It
is a skip — it ends the run, and `retries` never applies. The old
`resolve_match_id` used it for "WhoScored has not published a match id yet",
which read like patience and behaved like giving up. Skips are now reserved for
things that genuinely are not coming: a cancelled fixture, and an optional
analyst report.

### Resolving the match id

`resolve_match_id` tries four sources, cheapest first, and logs which one
answered:

1. Airflow Variable `match_id_<fixture_key>` (the manual override, below)
2. `whoscored_match_id` in `airflow/fixtures/arsenal_2026_27.json`
3. `fixtures.whoscored_match_id` in Postgres
4. A live WhoScored scrape

Only the fourth used to run. Ids baked into the calendar or already resolved
into Postgres bought the per-fixture DAG nothing, so every run re-gambled on
getting past the bot wall — which is how MW2 and MW3 ended up hand-patched.
Whatever is resolved is now written back to Postgres, and to the calendar when
it can be: the repo is bind-mounted from the host and owned by you, while the
container runs as `AIRFLOW_UID`, so that write is best effort and the task log
says so when it is refused. Postgres is what the pipeline reads, so nothing is
lost either way. To enable the write-back:

```bash
sudo chown -R :50000 airflow/fixtures && chmod -R g+w airflow/fixtures
```

The scrape itself tries, in order:

1. Arsenal's WhoScored team fixtures page
2. The Premier League tournament fixtures page
   (`…/stages/25544/fixtures/england-premier-league-2026-2027`, overridable via
   `GUNNERS_WHOSCORED_PL_FIXTURES_URL`)
3. The same grid rediscovered from `/regions/252/tournaments/2`, in case the
   season and stage ids in (2) have rolled — they do, every August

If none of those pages could even be *loaded*, that raises `FixtureLookupError`
rather than returning "not found". A bot wall and an unpublished fixture used to
be the same `None`, and the DAG reported both as "not published yet".

### Overriding a match id

If the resolver cannot find a fixture (renamed slug, cup replay, WhoScored
outage), set an Airflow Variable and the DAG uses it directly:

```
match_id_gw17_2026-12-26_crystal-palace_v_arsenal = 1903353
```

## The maintenance DAG

`arsenal_season_maintenance`, Mondays 06:00 UK:

1. `ensure_schema` — applies `db/schema.sql` (idempotent)
2. `reseed_calendar` — re-reads the fixtures JSON; picks up reschedules. Existing
   rows keep their status, resolved match id and attempt count; only date,
   kick-off and slug are refreshed.
3. `resolve_upcoming` — resolves WhoScored ids for anything inside 21 days, one
   browser session for the lot
4. `backfill_missed` — re-runs any fixture past kick-off that is not `ingested`,
   up to 5 attempts, recording `last_error` on the row
5. `season_report` — logs the fixture status breakdown and Arsenal's record

This is the safety net. If a per-fixture DAG misfires — postponement, bot wall,
a container restart — the match still lands within a week.

## When a fixture moves

```bash
# 1. edit the RAW table in airflow/fixtures/build_fixtures.py
# 2. regenerate + reseed
python airflow/fixtures/build_fixtures.py
python db/seed_fixtures.py
```

Airflow re-parses the DAG file and the new cron takes effect. The maintenance
DAG does step 2 for you every Monday, so if you only edit the JSON generator the
change propagates on its own.

For a postponement with no new date yet, mark it so the backfill leaves it alone:

```sql
UPDATE gunners.fixtures SET status = 'postponed' WHERE fixture_key = '...';
```

## Fixture state machine

```
scheduled ──► resolving ──► ready ──► ingesting ──► ingested
                                          │
                                          └──► failed ──► (retried by maintenance, max 5)

any ──► postponed   (manual, excluded from backfill)
```

## Quality gate

`quality/checks.py` runs 13 checks and blocks the load on any `error`-severity
failure. Warnings (thin xT coverage, odd pass share) are recorded but do not stop
the pipeline.

Errors: event count 800–3000, covers 90+ minutes, both halves present, exactly
two teams, 11 starters per side, no orphan player ids, coordinates on the pitch,
goal events match the final score.

A failing gate raises in the `validate` task, so the match shows up red in
Airflow and gets retried, rather than silently producing an empty dashboard —
which is exactly what the old always-pass stub allowed.

## Configuration

| Variable | Default | Meaning |
|---|---|---|
| `POST_MATCH_DELAY_MINUTES` | `30` | Minutes after the final whistle before the pipeline runs |
| `MATCH_DURATION_MINUTES` | `115` | Assumed match length: 90 + interval + stoppage |
| `PIPELINE_DELAY_HOURS` | _(unset)_ | Superseded. If set, overrides both above as a total offset from kick-off |
| `GUNNERS_ROOT` | `/opt/gunners` | Project root inside the container |
| `GUNNERS_DB_URL` | `postgresql://gunners:gunners@postgres:5432/gunners` | Warehouse DSN |
| `POSTGRES_PASSWORD` | `gunners` | Change this |
| `AIRFLOW_PASSWORD` | `admin` | Change this |

## Running one fixture by hand

```bash
docker compose exec airflow airflow dags trigger \
  arsenal_2026_2027_gw17_2026-12-26_crystal-palace_v_arsenal
```

Or without Airflow at all:

```python
from orchestrator import pipeline
pipeline.extract_match_json('data/raw/match_<job>.html')
pipeline.run_transform('<job>', season='2026/2027')
pipeline.run_quality('<job>')
pipeline.run_visualize('<job>')
pipeline.run_load('<job>', '2026/2027', fixture_key='gw17_...')
```
